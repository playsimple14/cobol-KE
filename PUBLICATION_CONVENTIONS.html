1. Which Research Convention?

The convention depends on your venue and positioning. Here are the three main paths:

Path A: Information Retrieval (IR) Convention

Best for: ACL, EMNLP, SIGIR, or specialized IR venues

Structure

1. Abstract (250 words)
2. Introduction (2-3 pages)
3. Related Work (2 pages) — IR baselines
4. Approach/Method (3-4 pages)
5. Evaluation (4-5 pages)
   - Dataset description
   - Metrics: Precision@k, Recall@k, NDCG
   - Baselines comparison
   - Statistical significance tests
6. Results (2-3 pages)
7. Discussion & Limitations (1-2 pages)
8. Conclusion (0.5 page)

Key IR Conventions:

  • Metrics: NDCG, Mean Reciprocal Rank (MRR), Precision@k, Recall@k, F1
  • Baselines: Minimum 3-5 baselines (Random, BM25, semantic search, state-of-art)
  • Significance testing: t-tests or bootstrap confidence intervals for results
  • Dataset: Multiple test sets with inter-annotator agreement (Cohen's kappa > 0.7)
  • Ablation study: Show contribution of each component (AST + Symbol + CallGraph)
IR Path Advantage Strong positioning if you have rigorous metrics + multiple baselines. Your ablation framework is already here.

Path B: Software Engineering Convention

Best for: ICSE, FSE, ASE, or SANER

Structure

1. Abstract (250 words)
2. Introduction (2 pages)
3. Problem & Motivation (1-2 pages)
4. Related Work (2 pages)
5. Approach (3-4 pages)
   - Koopa parser integration
   - AST chunking strategy
   - Symbol table slicing
   - Call graph expansion
6. Case Studies (3-5 pages)
   - Real COBOL programs
   - Before/after modernization scenario
7. Evaluation (3-4 pages)
   - Developer user study (n=3-10)
   - Time/effort savings
   - Comprehension metrics
8. Threats to Validity (1 page)
9. Conclusion (0.5 page)

Key SE Conventions:

  • Case studies: Real programs from industry (not toy examples)
  • Developer evaluation: Qualitative + quantitative (comprehension tests, time measurements)
  • Threats to validity: Detailed discussion of limitations (generalizability, bias, threats)
  • Practical focus: Show modernization workflow, time savings, business value
  • Reproducibility: Code + dataset repo, Docker setup for Koopa
SE Path Advantage Stronger with real case studies and developer studies. Requires recruiting participants (higher effort).

Path C: ML + Code Understanding Convention

Best for: NeurIPS, ICML, or ICLR (if you add learning component); or specialized ML4Code venues

Structure

1. Abstract (250 words)
2. Introduction (2 pages)
3. Related Work (2-3 pages)
   - Code RAG (RepoAgent, RepoCoder, CodePlan)
   - LLM code understanding
   - Structured retrieval
4. Method (3-4 pages)
   - Formal problem definition
   - Triple-source retrieval algorithm
   - Scoring function
   - Complexity analysis
5. Experiments (4-5 pages)
   - LLM-based evaluation
   - Hallucination rates
   - Grounding accuracy
6. Analysis (2 pages)
7. Conclusion (0.5 page)

Key ML Conventions:

  • Algorithm formalization: Pseudocode, complexity analysis
  • LLM evaluation: Run same query with different contexts; measure hallucination delta
  • Grounding metrics: Symbol resolution accuracy, condition correctness
  • Scaling: Show performance on progressively larger programs
  • Embedding experiments: Optional — can add learned component for ICML positioning
ML Path Advantage Highest impact venues. Best if you add learned component (e.g., learned scoring model). Otherwise position as "ML4Code application."

6. Common Pitfalls to Avoid

❌ Evaluation Pitfalls

  • No ground truth annotations (reviewers will ask for this first)
  • Cherry-picked examples instead of average performance
  • Missing ablations (don't just compare full system vs. naive)
  • No error analysis (what does your method fail on?)
  • Significance claims without statistical tests

❌ Reproducibility Pitfalls

  • Code not on GitHub (non-negotiable)
  • Missing dataset or synthetic-only data
  • Vague hyperparameters ("tuned on dev set")
  • No instructions for running Koopa parser
  • No Docker container for dependencies

❌ Positioning Pitfalls

  • "Better than naive RAG" (weak claim; compare to industry standards)
  • Overgeneralization ("Works for all COBOL" from 1 program)
  • Missing related work (reviewers know this space)
  • No discussion of limitations (threats to validity)
